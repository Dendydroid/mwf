6 Transcript is evidence, the slot map is state

There are two candidate designs for remembering a call, and the difference between them is the most consequential decision in this Part.

Design A. Keep the conversation. Every turn, send the whole transcript to the model and ask it what the booking currently is. The model has all the information; it should be able to tell you.

Design B. Keep a map of slot names to understood values. Every turn, send the model only the current utterance plus a small, rendered summary of what is already known, and ask it for one thing: what this utterance contributes. Code merges that contribution into the map.

Design A is smaller, obvious, and wrong. The reason is measurable.

The number that settles it

Dialogue state tracking — deriving the current slot values from a conversation — is a benchmarked task with two decades of work behind it. The metric is joint goal accuracy: the fraction of turns at which every slot is simultaneously correct. Not most slots. All of them, because a booking with the right date and the wrong reference number is not partially correct, it is wrong.

BenchmarkBest joint goal accuracyWhat it is made of
MultiWOZ 2.2~57%Typed dialogues, clean text, written by people who knew they were annotating
SpokenWOZ25.65%Spoken task-oriented dialogue: disfluencies, corrections, recognition errors

SpokenWOZ is the one that resembles a phone call, and on it the best tracker gets the whole state right about a quarter of the time. The best end-to-end system completes the caller's request in 52.1% of dialogues.

Those numbers are for systems designed to do state tracking. A general-purpose model asked to re-read a transcript each turn is not going to do better, and it has an additional failure mode the benchmarks do not measure: hallucination on slots the conversation never mentioned. That is a documented problem with LLM-driven state tracking — the model produces a plausible value for a slot nobody discussed.

Rule

Extract once, store forever. A value enters the slot map on the turn it was first understood, and after that it changes only through an explicit correction. It is never re-derived, and no later turn can quietly alter it by re-reading the transcript.

So what is the transcript for

Not nothing. Keep a rolling window of the last four to six turns, and use it for exactly one job: reference resolution. “Make it an hour later”, “no, the other one”, “same as last time” cannot be understood from the slot map, because the thing being referred to is in the words, not in the values.

The distinction to hold onto:

Transcript windowSlot map
IsEvidenceState
Answers“what did they mean by that?”“what do we have?”
SizeBounded: 4–6 turnsBounded: the form's fields
Written byAppend-only, verbatimCode, from a parsed value
If lostA pronoun becomes ambiguousThe booking is gone
AuthorityNoneTotal

The last row is the one that matters. If the window and the map disagree, the map is right. The window exists to help understand the next utterance, never to correct the record.

In this repo

ai_autocalls_rust keeps the map (flow.answers, session.memory) and does not keep a transcript at all — its understanding stage is an embedding matcher plus a small local model working one utterance at a time, so it never needed one. Adding the window to ai_assistant is a real addition, not a port, and it should be added as a window: a fixed-length ring, rendered into the prompt, never a growing list. A transcript that grows without bound is a context window that eventually overflows in the middle of a caller's sentence.

7 What a slot is made of

A slot is not a String in a map. It is at minimum six things, and leaving any of them out shows up later as a category of bug rather than a single one.

struct Slot {
    name:       String,        // "appointment_date"
    value:      Option<SlotValue>,   // parsed, normalised, typed
    raw:        Option<String>,      // what they actually said
    provenance: Provenance,    // Verified | Collected | Inferred
    confirmed:  bool,          // read back and agreed
    attempts:   u32,           // consecutive failures on this slot
}

Typed values, not strings

Speech recognition hands over a string, always. “The fifth of March nineteen eighty-seven”, “yes that's right” and “I five D F three” are all just text. A booking is not made of text; it is made of a date, a boolean and a reference code, and those three behave differently when stored, compared against a database row, and read back aloud.

So every answer passes through a parser that either produces a typed value or refuses. A typed slot value is a promise that this has already been understood; anything still shaped like raw speech never gets that far.

In this repo

forms/value.rs is this type, and its doc comment makes the argument better than a general rule could: read-back is a method on the value, not on the form, because a code must be spelled out (“I, 5, D, F, 3” — a synthesiser reads I5DF3 aloud as something like “eye-five-diff-three”, which no caller can check against the letters on their own letter), a date must be said the way that language says dates, and a choice must be read back with its human label rather than the database value. Putting it on the value means a new answer kind cannot forget: the compiler lists every match arm. Chapter 34 is the general version of this.

Keep the raw string too

The parsed value is what the system uses. The raw string is what the caller said, and it is worth keeping for the length of the call for three reasons: a correction often refers to the wording rather than the value, a mis-parse is only diagnosable if the input survives, and reading back the raw string is sometimes the fastest way to resolve a disagreement.

It is also personal data, which is Part VIII's problem and needs a retention decision rather than an accident.

Provenance: the field that prevents an incident

This is the one most implementations leave out, and the one worth adding on day one.

Verified
Written only from an authoritative source — a database row, a lookup, an API response. A customer id, an account balance, a confirmed booking reference. Never written from a model's output, under any circumstances.
Collected
Came from the caller, through parse → normalise → (usually) confirm. A preferred date, a name, a choice from a list. Trusted enough to act on once confirmed, and never treated as authoritative about the outside world.
Inferred
Derived by code from other slots — a duration computed from a start and an end, a default filled in from business rules. Recomputed when its inputs change, never edited directly.
Trap

A model asked to produce a customer id will produce one. It will be the right length, the right shape, and entirely invented. If that value reaches a slot marked as if it came from a lookup, the system then reads it back to the caller with confidence, attaches it to a submission, and possibly loads somebody else's record with it. That is not a UX bug; under GDPR it is a personal-data breach involving the wrong data subject. The type system should make it impossible: a Verified slot has a constructor that only the lookup code can reach.

In this repo

ai_autocalls_rust encodes half of this already: CallSession::identified_as carries the comment “never set by anything except a successful lookup”. That is provenance expressed as a convention. Promoting it from a comment to a type is a small change with a large blast radius, and it is the right first thing to build when ai_assistant grows slots of its own.

Confirmed, and attempts

confirmed is a property of the slot, not of the turn, because a correction three questions later has to clear it. attempts counts consecutive failures on the current question and drives the escalation ladder in Chapter 35.

One subtlety worth stealing: ai_autocalls_rust's attempts field is explicitly not incremented when the caller asks a reasonable question instead of answering — “they did not fail, they asked something”. Counting a mid-form question as a recognition failure is how a system ends up transferring a perfectly cooperative caller to a human for the crime of being curious.

8 The predicate that moves the call

A step is complete when its slots satisfy a boolean expression over values the system already holds:

fn step_complete(step: &Step, slots: &SlotMap) -> bool {
    step.required.iter().all(|name| {
        match slots.get(name) {
            Some(slot) => slot.value.is_some()
                       && slot.valid()
                       && (!step.needs_confirmation(name) || slot.confirmed),
            None => false,
        }
    })
}

There is no model call in that function and there must never be one. Every term is a fact the system wrote itself.

Why this is worth being dogmatic about

The alternative — asking the model “is this step complete?” — is attractive because it handles cases the predicate does not: the caller who says “that's everything you need, right?”, the one who answers three questions in one breath. It works in testing. It fails in two specific ways that testing does not catch.

First, a model asked for a boolean always returns one. There is no “I could not tell” token. When the caller says something that does not answer the question — “hold on, my dog is barking” — the model still emits true or false, and a true there is a submission with a missing field that nothing downstream checks.

Second, it is not reproducible. When a caller reports that the booking lost their reference number, a predicate can be evaluated against the stored slots and will give the same answer it gave during the call. A model call cannot be replayed with the same guarantee, which means the bug cannot be confirmed, only guessed at.

Two tiers of validation

Rasa's split is the one worth copying, because implementations converge on it anyway. Domain-level validation lives with the slot definition and enforces universal, technical constraints — type, format, range — whenever the slot is set. Business validation lives with the form and enforces rules that depend on context.

TierExampleWhere it lives
Domain / technical“a date is a date”; a reference code matches the formatThe parser and the slot type — always runs, every form
Business“that date is a Sunday and we are closed”; “that slot is taken”The form's validator — may need a database call

The distinction is not academic: a domain failure means “I did not understand” and should be re-prompted; a business failure means “I understood you perfectly and the answer is no” and needs a completely different sentence. Collapsing them produces the maddening interaction where a system responds to a perfectly clear request by asking the caller to repeat themselves.

Rule

A step transition is a pure function of stored state. If evaluating it requires a model call, a network call or the current time, the state is incomplete — add the missing slot rather than reaching outside the function.

9 Mixed initiative: over-answering, correcting, digressing

Directed dialogue — one question, one answer, in order — is easy to build and unpleasant to use. Real callers do three things it does not handle, and all three were named in the VoiceXML specification before any of the current tooling existed.

Over-answering

You asked for a date. They said “Tuesday at three, and it's for two people”. Three slots arrived; one was requested.

The mechanism is straightforward once the slot map exists: the model returns a map of contributions rather than a single value, and code merges all of them, then re-evaluates which question to ask next. What matters is that the extraction schema for a step includes every slot in the form, not just the current one — otherwise the extra values are discarded silently and the caller is asked again for something they already said, which is the single most irritating thing a phone system does.

Cost: the schema is larger, so more tokens are generated per turn (Chapter 21). Worth it.

Correcting

“Actually, make it Wednesday.” “No, I said fifteen .” A correction is a write to a slot that already has a value, and it has three consequences that must all happen together:

  1. The value is replaced.
  2. confirmed is cleared — the old read-back agreed to a value that no longer exists.
  3. Any Inferred slot computed from it is recomputed, and any Verified slot obtained using it (an availability check, a lookup) is invalidated.

Point three is the one that gets missed. If “Tuesday” was checked against a calendar and “Wednesday” was not, the system now holds an availability confirmation for a date nobody asked for.

Trap

Corrections arrive most often during the final read-back, which is exactly where the code is least prepared for them, because the review stage is usually written as a yes/no. “No — the date's wrong” is not a no; it is a correction to one field plus an implicit yes to the rest. A review stage that can only accept or restart will make callers re-answer four correct questions to fix one wrong one.

Digressing

Mid-form, the caller asks something unrelated: “wait, how much does this cost?” The requirement is to answer it and then return to exactly where the form was, without losing the place and without counting the digression as a failure.

This needs one design decision: who looks at the utterance first? If the answer parser looks first, a question that happens to parse as free text gets swallowed as an answer. If the question classifier looks first, a legitimate answer that resembles a question gets diverted.

In this repo

ai_autocalls_rust resolves this per field kind, and the comment on flow.rs::interpretation_for insists the choice was “measured, not stylistic”: everything parses as free text, so a text field must let the question subscriber look first, and every other kind must not. A typed field is its own filter — “how much does this cost?” does not parse as a date — so the parser can safely go first and the ambiguity never arises.

That is a rule worth generalising: the more constrained the expected answer, the earlier the parser may look.

The other half: repeating

“Sorry, what?” deserves a mention because it is trivial to implement and disproportionately valuable. Keep the last sentence said, verbatim, and repeat it unchanged. Rephrasing is actively worse: a caller who did not catch a question wants the same question again, and different wording makes them think they misheard something else. CallSession::last_prompt exists for exactly this.

10 Where call state lives

Three questions: what is the key, what store, and when does it disappear.

The key comes from the phone system

The caller's side owns the call. It already has an identifier for it, it sends that identifier on every request, and inventing a second one creates a correlation problem for no benefit — particularly when a caller's data has to be found again later (Chapter 44).

One consequence worth designing in deliberately: a request with no call id behaves exactly as the stateless endpoint does today — one question, one answer, nothing remembered. That keeps every existing test and any integration that does not send one working unchanged, and it means statefulness is opt-in rather than a breaking change.

Hot in Redis, cold in Postgres

The production pattern separates state by temperature, and the reasoning is about write volume rather than fashion:

Redis — hotPostgres — cold
HoldsThe live call session: slots, stage, attempts, turn window, last promptThe finished submission, and anything with a legal or business life after the call
WrittenEvery turnOnce, at completion
ReadEvery turnRarely, and by other systems
LifetimeTTL, minutes to hoursA retention policy (Chapter 44)
If lostThe call in progress is confused — badThe booking never happened — unacceptable

A call session is worthless half an hour after the call ends and is written on every single turn. Putting it in Postgres means a durable write per turn for data nobody will ever read again. Redis expires it without a cleanup job and costs a fraction of a millisecond.

One key, one round trip

Store the session as a single serialised value under one key rather than as a hash with a field per slot. The whole session loads in one operation, the field count does not grow as the conversation goes on, and there is no window in which half the slots have been updated.

The rolling turn window belongs inside that same value, as a fixed-length ring. If it is a separate list it needs its own trimming, its own TTL, and its own failure mode where the window survives a session that did not.

Measure this

The session TTL, against how long calls actually last. cache_settings.session_ttl_days = 1 in settings.toml today — correct for a cookie session, enormous for a call that lasts four minutes. A day of TTL on call sessions is a day of personal data sitting in Redis after every call (Chapter 44). Measure the 99th-percentile call duration and set the TTL to a small multiple of it; an hour is generous.

Rule

Write the thing that must survive to durable storage before telling the caller it is done, and never make the caller wait on a third party. Save the submission inside the request; send it onward in the background. A booking whose delivery permanently fails is still a booking — the row stays, marked failed, with the attempt count and the last error. Chapter 31 covers the ordering in full.

11 Shaping it in Rust

Everything above is language-neutral. This chapter is about the shape the code takes, and it draws entirely on a design that already exists one directory across.

The stage is an enum, and the enum is the documentation

pub enum FormStage {
    ConfirmingStart,                // "you'd like to book - is that right?"
    ChoosingEntryMode,              // answer the questions, or be looked up
    Collecting { index: usize },    // waiting for field N
    ConfirmingField { index: usize },// waiting for a yes/no on field N
    ReviewingSummary,               // waiting for a yes/no on all of it
}

Five variants, and the whole shape of a form-filling call is visible in them. Two details are worth noticing.

ConfirmingStart exists because discovering at question four that the caller wanted something else wastes far more of their time than one exchange up front. ChoosingEntryMode exists because “give me something that identifies you and I will look the rest up” is a fundamentally different route through the same form, and modelling it as a route rather than as a branch inside every step keeps the steps simple.

Why not typestate

Rust's typestate pattern — one type per stage, transitions consuming self — makes illegal transitions unrepresentable, which is exactly what a state machine wants. It is the wrong tool here for one reason: this state is serialised to Redis and back on every turn. Typestate encodes the state in the type, and a value arriving from Redis has no type until it has been deserialised, at which point a runtime match is unavoidable anyway. The enum is honest about that; typestate would add ceremony around the same match.

Keep typestate for things that live inside one request. Use a serialisable enum for anything that crosses a turn boundary.

Events, not a call chain

The structural decision worth borrowing is how a turn is dispatched. The obvious implementation is a function that calls a function that calls a function, branching on stage. The alternative is to treat every step of the call as an event and every step's code as a subscriber that asked for it, ordered by a declared priority.

In this repo

ai_autocalls_rust's events/mod.rs is worth reading in full before designing anything here; it records what the shape bought.

  • The whole flow is one readable list — the CallEvent enum — rather than a chain four files deep. The file it replaced was 1,200 lines in which the state machine, the wording, the parsing, the database writes and the mid-form question handling were one call graph.
  • A question asked in the middle of a form became literally separate code from filling in that step: form_question.rs and form_step.rs are two files that never call each other, ordered by priority on the same event. Before, one if inside a 100-line function decided both.
  • Walking a form stopped needing mutually recursive async fns. Entering a field that is already answered simply dispatches the next FormStepReached, so what used to require Box::pin — “recursion in an async fn requires boxing” — is now the dispatcher's ordinary re-entry.
  • Adding a step to the call is three edits: a variant, a subscriber, a registration. The route handler never changes again, which is the point.

The naming rule that enforces Chapter 4

One convention from that file deserves to be copied verbatim, because it puts the “model extracts, code decides” rule into the type system:

A name ending in Request means the caller's own words, as plain data. CallRequest, FormConfirmationRequest, FormStepDataRequest all carry a string the caller said and nothing else — not a decision, not an instruction, not a command. Every other name is a fact in the past tense: FormRequestConfirmed, FormStepDataFilled, FormFinished. ai_autocalls_rust, app/src/events/mod.rs

Whether the words turn out to be an answer, a question or noise is decided by subscribers, not by the event. A developer who types FormStepDataFilled { text } has made a type error in the domain sense before they have made one in the compiler's.

Forms in data, not in code

The last structural decision: a form is a row in a database, not a Rust module. ai_autocalls_rust defines forms, their fields, the field kinds and the option lists in Postgres, and its extension guide marks “add a new conversational form” as no code. Only a genuinely new kind of answer needs a new parser, and that is a small file with a single responsibility.

This matters more than it looks, and Chapter 16 is why: the same definition that validates an answer is the definition that renders the schema into the prompt. One source, two consumers. A form defined in Rust and described again in a prompt file is two sources that will drift, silently, on a Tuesday.
