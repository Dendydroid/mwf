Evaluation & observability

A system with a language model in it has no compiler for the part that matters. A one-word prompt edit can change behaviour and nothing will say so. The substitute is a measurement loop, and the reason this Part comes after the design chapters rather than before is that most of what it measures only exists once the state in Part II does.

38 Three loops

Different failures are caught at different speeds and at different costs. The mistake is to build only the slowest one.

LoopRuns in CatchesCannot catch
UnitMilliseconds Parsers, validators, the step predicate, read-back rendering, prompt assembly Anything about the model
ScenarioMinutes Routing, extraction, the shape of a whole dialogue, regressions from a prompt edit Real audio, real accents, real interruptions
ProductionContinuously Everything the other two do not anticipate Anything, before it reaches a caller

Loop 1 is mostly already here

The 19 library tests in this repository are a good example of what belongs in this loop, and two of them are worth naming as patterns rather than as tests.

keys_the_code_has_never_heard_of_survive_the_round_trip asserts a design property, not a behaviour: if it ever needs a Rust change to keep passing, extending the schema has stopped being free. That is a test of the architecture, and the comment says so.

a_server_that_never_answers_is_reported_as_a_timeout binds a socket, accepts, and never replies — which is what a busy vLLM looks like from the client side. It tests an error classification that would otherwise only be exercised by the incident it was written for.

Everything added in Part II belongs in this loop and is cheap to test there: a parser is a pure function from a string to an optional value, a validator is a predicate, the step predicate is a predicate, and read-back rendering is a total function over an enum.

Loop 2 is the one that does not exist yet

A scenario is a scripted conversation plus the assertions that should hold at the end: which function was selected, which slots were filled with which values, how many turns it took, whether it escalated.

scenario: reschedule, caller corrects the date mid-form
  turns:
    - say: "hi, I need to move my appointment"
      expect: { selected_function: reschedule_appointment }
    - say: "it's for the second of October"
      expect: { slot.appointment_date: 2026-10-02 }
    - say: "actually no, make it the third"
      expect: { slot.appointment_date: 2026-10-03,
                slot.appointment_date.confirmed: false }   // ch.9
  end:
    turns_taken: { max: 6 }
    escalated: false

The practical guidance on sizing: 40 to 60 scenarios is a workable starting suite, and the baseline is the recorded behaviour of the build currently trusted in production, captured as a fixed set that can be replayed against any future build. A regression in any one of them blocks the release.

Rule

The scenario suite runs on every prompt change, not only on every code change. Hot reload means a prompt edit ships without a build, which makes it the most likely source of an unreviewed regression and the least likely to be tested. A prompt edit that has not run the suite is an untested deploy.

Where an LLM judge is legitimate

Assertions on structured fields — which function, which slot value, how many turns — are exact and need no judge. Assertions on the sentence do need one, and that is where a model-graded rubric belongs: was it in the right language, did it ask exactly one question, did it avoid repeating the previous turn verbatim, did it read the date back in a spoken form.

The line: a judge is for properties of prose with no exact answer. It is not a substitute for an assertion that could have been exact. A suite that grades “did it extract the right date?” with a model has replaced a measurement with an opinion.

39 The metrics that matter

Grouped by the question they answer, because a dashboard of forty numbers answers none.

Is it working for callers

MetricNotes
Task completion rateOf calls that started a form, how many produced a submission. The headline number
Containment rateResolved without a human. Watch alongside completion — containment alone rewards refusing to escalate
Turns to completionDistribution, not mean. A long tail is where the confirmation and re-prompt problems show
Escalation rate, by triggerWhich of Chapter 36's triggers fired. A shift between triggers is the early warning

Is the model behaving

MetricNotes

Truncation rateTruncated over total. Any non-zero value means max_tokens needs re-deriving
Routing distributionShare per selected_function. A sudden shift after a prompt edit is the fastest regression signal available
Slot extraction accuracyPer slot, against confirmed values. The slot that is always corrected is a prompt problem, not a caller problem

Is it fast enough

MetricNotes
Time to first tokenThe one comparable to the 375 ms budget (Chapter 3). Not currently measured
Total turn timep50 / p95 / p99. The mean is not useful

Rule

Percentiles, never means, for anything on the path to a caller's ear. A mean turn time of 1.2 s with a p95 of 6 s is a system where one call in twenty has the agent talking over the caller, and the mean says it is fine.

Offline and online are the same metrics

The pattern that works: the metrics scored in the scenario suite are the same ones charted live in production, so a regression caught offline and an incident caught online are expressed in the same units. Production data then feeds back — a call that went wrong becomes a scenario, and the suite grows from real failures rather than from imagination.

40 Tracing a call

OpenTelemetry's GenAI semantic conventions define a standard vocabulary for model invocations, tool calls and agent runs, so a span from one framework looks like a span from a raw API call. Adopting them costs almost nothing at this stage and saves a migration later.

The span tree

call            trace, id = call_id                     // the whole conversation
  turn          span, one per request
    prompt.assemble                                     // ch.18; carries the hash
    gen_ai.chat  gen_ai.request.model, .usage.*, .response.finish_reasons
    parse                                               // ch.25 error variant on failure
    slots.merge                                         // which slots changed, and from what
    step.evaluate                                       // ch.8 predicate, and its result
  turn
  ...
  submission.commit                                     // ch.31

Using call_id as the trace id is the decision that makes this useful: every turn of a call is one trace, and a support question about a call becomes a single lookup rather than a log search.

The attributes to emit

AttributeValue
gen_ai.request.modelQwen/Qwen2.5-7B-Instruct-AWQ
gen_ai.usage.input_tokens / output_tokensFrom the response
gen_ai.response.finish_reasonsThe length / stop distinction already parsed
prompt.hashChapter 18 — the binding between a call and a prompt version
form.key, form.stage, slot.nameProject-specific, and worth as much as the standard ones

Two metric instruments are worth wiring on day one: gen_ai.client.operation.duration and gen_ai.client.token.usage, both histograms. Between them they cover most of Chapter 39's third table.

Rule

Prompts and messages go in span events, not span attributes. Attributes are indexed and retained on every span; the content is large, variable, and — in this system — personal data. Events can be sampled, dropped and redacted independently, which is the whole of Chapter 41.

In this repo

tracing is already in the stack, rolling daily to LOG_DIR with ANSI off, and main.rs loads settings before initialising it because LOG_DIR decides where logging goes. Adding tracing-opentelemetry is a subscriber layer, not a rewrite.

One trap is already documented and worth re-reading: .env had three RUST_LOG lines, and the last one won — mwf=trace,tower_http=debug, naming a crate this project does not have, which filters out the application's own logs. Harmless while tracing initialised first; it would have made the new log files empty. The general lesson is that a filter naming a crate that does not exist fails silently and produces a system that looks healthy because it says nothing.

41 What to log, and what must never be

The known gap, from context.md:

request_text is logged verbatim. On real calls that is personal data (GDPR retention/erasure). Redact before this touches a phone line. ai_assistant, context.md — Known gaps

That assessment is correct and Part VIII is the full treatment. This chapter is the operational half: what a log line should contain so that it is useful without being a liability.

The three tiers

TierContentsRetention
Always call_id, turn number, stage, selected function, slot names changed, latency, token counts, error variant, prompt hash Ordinary operational retention. Contains no caller content
Redacted Utterance and generated sentence with entities masked: "my name is [PERSON] and my reference is [ID]" Short. Justified, documented, enforced (Chapter 44)
Never Raw utterance, raw slot values, the assembled prompt, the API key, anything marked Verified —

The first tier is the one that does the diagnostic work. Chapter 16's scenario — a slot renamed in one place — is fully diagnosable from slot names and the predicate's result, with no caller content at all: a step that keeps re-asking with an unchanged slot map is visible in the structure of the trace.

Trap

The debug log written during development is the one that leaks. debug!(content, truncated, "vLLM answered") in vllm.rs logs the model's complete output — which is exactly what is wanted while iterating on a prompt, and which contains the caller's name, their date of birth and their reference number the moment this is on a real line. It is gated behind RUST_LOG, and RUST_LOG=debug gets set in production by someone diagnosing an incident at two in the morning.

Redaction belongs in the field, not in the level. A value that must not be logged should be a type whose Debug and Display print [redacted], so no log level can reveal it and no future call site can forget.

Rule

Log the shape of the turn, not its contents. Slot names, not slot values. Which function, not what they said. A prompt hash, not a prompt. Every one of those is enough to debug the class of failure it belongs to, and none of them is personal data.
