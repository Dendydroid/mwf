How to read this book

This is a reference, not a tutorial. It is meant to sit open next to an editor, be opened at a chapter, and be closed again. Nothing after this page depends on having read the page before it.

What it is for

ai_assistant currently does one thing well: it takes an utterance, sends it to vLLM under a file-backed system prompt, and returns a JSON decision whose only mandatory key is humanlike_sentence_answer. It is stateless by design, and that design is about to stop being enough. The last section of context.md reaches toward per-call state, multi-step form filling, and a prompt architecture that can grow past a single text file.

This book is the reading behind that step, compressed. It collects what the voice-AI industry, the task-oriented-dialogue literature, and the vLLM documentation have already settled, and lands each finding on the code that exists today — vllm.rs, settings.toml, the ActionDecision pass-through — rather than leaving it as general advice.

The order it is in

Parts I–VIII run from the outside in and then out again: where you sit, then the three layers you own (dialogue, prompt, serving), then the three disciplines that keep them alive in production (reliability, voice, evaluation), then compliance, which is the one that can stop the project rather than merely degrade it.

Part IX is the audio layer — speech recognition, turn detection, barge-in, telephony — and it is last on purpose. This service receives text, not audio. Someone else's system does the listening. But that system sets the latency you may spend, explains why transcripts arrive missing their punctuation, and decides what “the caller said” even means when they interrupted halfway through. Earlier chapters point into it with → §IX.n when that context helps; none of them require it.

The marks in the margin

Rule

A thing to do, stated as an instruction. These are the sentences to copy into a code comment or a pull-request checklist. There are thirty-five in the book and they are all collected in Appendix B.

Trap

A failure that looks like something else. These are the expensive ones: the bug whose symptom points at the wrong layer, the setting that is harmless until an unrelated change makes it fatal. The 502 described in context.md was one of these.

In this repo

Where the general point meets the actual code — a file, a line, a configured value, or a decision already taken in ai_autocalls_rust that this project can borrow rather than rediscover.

Measure this

A number that should not be guessed. Each one names what to measure, what a good value looks like elsewhere, and what to do when the measurement disagrees with the book.

Two conventions worth knowing

Numbers carry provenance. A figure such as “1,115 ms mouth-to-ear” is somebody's published budget, not a law; a figure such as “0.6–2.8 s per turn” was measured on this machine and recorded in context.md. The two are always distinguished, because the first is a target to argue with and the second is a fact to design around.

Citations are terse in the body and complete in Appendix A. Where a chapter says “LiveKit's turn-detection guidance”, Appendix A has the URL, one line on what the source is good for, and one line on what to skip. Nothing is cited that was not actually retrieved, and the entries read in full are marked as such — the rest were consulted far enough to source a specific claim and no further.

If you only read four chapters

Chapter 3, because it reframes every latency decision in the project. Chapter 7, because slot provenance is the difference between a bug and a data-protection incident. Chapter 16, because one manifest rendering both the prompt and the validator is the single rule that prevents the worst class of bug in a system like this. And Chapter 27, because reordering the output schema buys latency that costs nothing else.
