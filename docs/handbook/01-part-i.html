Before any decision about slots, prompts or timeouts makes sense, three things have to be settled: what this service actually is, whose latency it is spending, and which of the two kinds of LLM system it belongs to. All three are commonly got wrong, and each one costs a rewrite.

1 Text in, one sentence out

Strip away the HTTP, the JSON and the GPU and this service is one function:

turn : (utterance, call_state) -> (sentence, call_state')

Today the second argument and the second return value are missing. POST /assistant/handle-request takes request_text and an optional language, and returns a decision. Nothing carries from one call of the function to the next. That is a deliberate simplification, not an oversight, and context.md records it as such: “stateless by design”. Most of Part II is about what it costs to put the missing arguments back.

What does not change when state arrives is the shape of the return value. Whatever else a turn produces, it produces one sentence the caller hears. That is the promise the endpoint makes, and it is why ActionDecision names exactly one key.

Three jobs, and only two of them belong to the model

Every turn does three things:

Understand
Turn a noisy, ungrammatical, possibly mid-sentence utterance into something structured. “yeah no the fifth is bad, make it the sixth” is a date correction. A model is very good at this and nothing else is.
Decide
Given what was understood and what the call already knows, work out what happens next: which function to run, whether the step is complete, whether to confirm, whether to hand off. This is a predicate over known values.
Phrase
Produce the sentence. Natural, in the caller's language, in the right register, without repeating the exact wording used two turns ago. Again, a model is very good at this and a table of static strings is not.

The middle one is the whole argument of this book. It is the job that looks like it belongs to the model — the model is right there, it has all the context, it can obviously answer “should we move on?” — and it is the job that must not be given to it. Chapter 4 makes the case in full; Part II turns it into code.

Rule

The model extracts and the model phrases. Code decides. Any turn where a state transition depends on a generated token is a turn that can silently take the wrong branch, and no amount of prompt work fixes it — it makes it rarer, which is worse, because rare wrong branches are the ones that reach production.

The path a turn takes through this repository

            +-- ChatCompletionRequest {          // temperature 0.0, max_tokens 256

          200 {"answer": "...", "selected_function": "...", ...}

Four things in that path are decisions rather than plumbing, and each gets a chapter of its own: the prompt is a file re-read per turn (Chapter 18), the decision is a pass-through map rather than a struct (Chapter 16), decoding is constrained to JSON (Chapter 22), and the failure modes are distinguished by type rather than collapsed into one (Chapter 25).

What the pass-through design buys, and what it costs

ActionDecision is an unusual shape and worth understanding before anything is built on top of it. It names humanlike_sentence_answer and flattens everything else into a serde_json::Map:

pub struct ActionDecision {
    pub humanlike_sentence_answer: String,

    #[serde(flatten)]
    pub fields: Map<String, Value>,
}

The benefit is real and it is the reason prompt iteration on this project is fast: adding urgency to the schema in the prompt file makes urgency appear in the API response and as a badge in the mimic client, with no Rust change and no rebuild. context.md records this being exercised mid-session — two keys added, used on the next turn, then removed — which is exactly the loop prompt work is made of.

The cost is that the compiler has stopped helping for every key except one. If the prompt asks for anger_level and the model returns angerLevel, nothing fails; the badge silently disappears and any code reading fields["anger_level"] gets None. The existing tests cover the round trip and the key ordering, but they cannot cover a key that does not exist yet.

In this repo

This trade is correct while the extra keys are observational — badges, log fields, things a human reads. It stops being correct the moment a key drives behaviour. The first time code branches on fields["is_hanging_up"], that key has earned a named field and a test, and the pass-through map should hold only what remains decorative. Chapter 16 gives the rule for deciding which is which.

2 Three architectures, and which one you are in

There are two ways to build a voice agent in 2026, and this service is a component of the second one rather than an instance of either.

Bundled speech-to-speech

A single model takes audio in and emits audio out: OpenAI's Realtime API, Gemini Live. One WebSocket carries the whole loop. Time-to-first-audio lands around 300–500 ms on a warm connection, and the model hears the caller's actual voice, so hesitation, laughter and accent survive into the response instead of being flattened into a transcript.

What you give up is control. Tool calling is less mature, argument validation is looser, and the per-stage timings are inside somebody else's box. The consistent industry guidance is that speech-to-speech suits agents with one to three tools and forgiving argument validation — search, lookup, simple state queries.

Cascaded

Three components in a row: speech-to-text, then a language model, then text-to-speech, with a turn-detection layer deciding when the caller has stopped talking. This dominates production deployments. Each component can be replaced without touching the others, every stage emits its own metrics, and structured output can be enforced properly because the middle stage is an ordinary LLM endpoint.

The price is latency: a well-built cascade lands at 600–1,200 ms time-to-first-audio, and three services means three independent failure surfaces.

For agents needing five or more tools with strict schema enforcement — booking, payments, healthcare intake, structured form filling — cascaded is the safer default. That description is this project exactly.

Where this service actually sits

It is the middle box of a cascade someone else owns. The phone system does the listening, the endpointing and the speaking; it hands over text and expects a sentence back. ai_autocalls_rust's README states the arrangement plainly: “The backend a phone system calls during a live call. The caller's words arrive as text.”

Concern Owned by the phone system Owned by this service

Two consequences follow, and they pull in opposite directions.

The comfortable one: a whole class of hard problems — acoustic echo, jitter, μ-law, barge-in reconciliation — is not yours. Part IX covers them so that their effects are recognisable, not so that they can be fixed here.

The uncomfortable one: you are spending a budget you did not set and cannot see. The phone system has already spent several hundred milliseconds before the first byte of request_text arrives, and will spend more after the response leaves. What remains is the next chapter.

Rule

Design as though the components around you will be replaced, because in a cascade they are. Nothing in this service should depend on which speech recogniser produced the text or which synthesiser will read it — with one deliberate exception, the normalisation rules in Chapter 34, which are written against a capability (SSML) rather than a vendor.

3 The latency budget you are already spending

This is the chapter that changes how the rest of the project is read, so it comes early and it is short.

The budget, as the industry states it

Twilio's engineering guidance for voice agents allocates the round trip like this:

StageBudgetWhat it covers
Speech-to-text350 msMostly endpointing, not acoustic compute
Language model375 msTo first token, not to a complete answer
Text-to-speech100 msTo first audio byte
Median mouth-to-ear1,115 msTransport and buffering account for the remainder

The human constraint behind the number: response delays past 500–700 ms start to read as unnatural, and a caller who thinks the line has gone dead starts talking again — which triggers barge-in, discards the answer being synthesised, and costs another full turn.

The budget, as this project is spending it

context.md records the measurement: “Normal turns measure 0.6–2.8 s.” That is wall-clock for VllmClient::classify — request out, complete JSON parsed.

BudgetMeasured hereRatio
LLM stage, best observed375 ms600 ms1.6×
LLM stage, worst observed375 ms2,800 ms7.5×
Whole conversational budget1,115 ms600–2,800 ms0.5–2.5×

The best case consumes more than half the entire mouth-to-ear budget on its own. The worst case exceeds it two and a half times over, before the phone system has spent a millisecond on recognising or speaking.

This is not a criticism of the implementation. It is the expected shape: the language model is normally the largest single contributor to time-to-first-audio, which is precisely why the optimisations that matter are all about overlapping it with something else rather than making it faster.

Why the comparison is not quite fair, and why it still stands

The 375 ms figure is time to first token. The 600–2,800 ms figure is time to the last token, because this client is not streaming: classify awaits the complete response, then parses it. The like-for-like comparison does not exist yet, which is itself the finding.

Measure this

Time to first token, separately from total turn time. Today neither is recorded as a metric; only the total appears incidentally in a log line. Add both to the span described in Chapter 40 and watch p95, not the mean — benchmark disagreements between voice vendors are almost always percentile differences rather than model differences.

Elsewhere: ~820 ms p50 time-to-first-token has been measured for a frontier hosted model from cloud regions. A locally served 7B on a warm GPU should beat that comfortably; if it does not, the problem is queueing or prefix-cache misses rather than the model.

What actually recovers the budget

Three things, none of which is a faster GPU:

  1. Stream, and chunk at sentence boundaries. The single largest recovery available in a cascade comes from feeding tokens into synthesis as they arrive rather than after the answer completes. Chapter 27 covers the mechanics, including a change specific to this schema that costs nothing.
  2. Stop generating tokens nobody hears. Every key in the output schema is generated serially. The current schema is eight keys and about 100 tokens; only one of them reaches the caller's ear.
  3. Keep the prefix cached. A stable prompt prefix cuts time-to-first-token substantially — 60–80% reductions are reported for chat workloads with long shared system prompts. Chapter 26 covers what breaks it.

What timeout_seconds = 120 actually is

Read against a 375 ms budget, the configured timeout is roughly 320 times the target. That is not a contradiction — it is two different numbers doing two different jobs, and the project currently has only one of them.

settings.toml is explicit about what the 120 is for: “This is not sized for that, it is sized for the bad day.” It exists so that a cold or contended GPU produces a slow answer instead of a 504. That is correct. What is missing is the other number: the latency at which the answer has stopped being useful because the caller has already started talking again.

Rule

Keep three latency numbers, not one. A target (what a good turn costs — the thing to optimise), an alert threshold (p95 crossing a line that predicts callers talking over the agent), and a timeout (the absurd value, where waiting longer cannot help anyone). Today this project has only the third, and it is easy to mistake it for the first.

Trap

A generous timeout hides a latency regression completely. Nothing fails, no error is logged, no alert fires — and callers start interrupting the agent, which surfaces as a rise in barge-in and no-match events on the phone system's dashboard, in a different system, owned by a different team. The 502 in context.md was visible only because the timeout was too tight. Raising it to 120 s fixed the symptom and removed the alarm.

4 This is a workflow, not an agent

The distinction is Anthropic's and it is more load-bearing than it sounds. Workflows orchestrate models and tools through predefined code paths. Agents let the model direct its own process and tool usage. The guidance for choosing is about predictability: agents suit open-ended problems where the required number of steps cannot be predicted and a fixed path cannot be hardcoded.

A booking form has four steps. They are known at design time, they are in a database table, and their order is a business decision rather than a modelling one. This is a workflow.

Which workflow, precisely

Two of the five named patterns, composed:

Routing
Classify the input, dispatch to a specialised handler. This is exactly what selected_function does today. The pattern's stated benefit is separation of concerns — optimising the prompt for cancellations cannot degrade invoice handling, because they are different handlers.
Prompt chaining
Decompose into sequential steps where each call handles one thing. This is what multi-step form filling becomes: each step is a small, focused call with a small, focused schema, rather than one prompt trying to hold the whole booking in its head.

The guidance that matters most here is about restraint: start with simple prompts, optimise with evaluation, and add agentic machinery only when simpler solutions demonstrably fall short. Most successful production systems are deterministic code with LLM decision points placed deliberately — not autonomous loops.

Own the control flow

The 12-Factor Agents formulation is blunt and worth keeping: the model may choose the next action, but the application owns the loop, the stop conditions, the retries, the approval gates and the budget ceilings. Two neighbouring factors matter as much: unify execution state with business state (factor 5), and make the agent a stateless reducer (factor 12) — a function from state and input to new state, with nothing hidden in the model's head between turns.

That last one describes the target design for this service almost exactly, and it is worth noticing that the current stateless endpoint is already a degenerate case of it. Adding state does not mean abandoning the shape; it means passing the state in and getting it back out, explicitly, on every turn.

The division of labour, concretely

Give to the modelKeep in code
Reading a mangled transcript as a date Whether that date is in the future and inside business hours
Noticing the caller corrected themselves Which slot the correction applies to, and clearing its confirmation
Detecting the language Which language the rest of the call is conducted in
Judging that the caller sounds angry The threshold at which anger triggers a hand-off, and the counter
Phrasing the question naturally, differently each retry Which question is asked, and after how many failures to stop asking
Summarising the call for a human agent The structured fields handed over alongside that summary
Trap

The tempting prompt line is "is_step_complete": bool. It works in testing, because in testing the caller answers the question that was asked. It fails when the caller says “actually, hold on” — a model that has been asked for a boolean will produce one, and a true there is a booking with a missing field that nobody notices until delivery. The predicate in Chapter 8 has the same job and cannot be talked into the wrong answer.

In this repo

ai_autocalls_rust settled this and left the artefact behind: events/mod.rs documents that a name ending in Request carries the caller's own words, as plain data — not a decision, not an instruction. CallRequest, FormConfirmationRequest, FormStepDataRequest all hold a string and nothing else. Whether those words are an answer, a question or noise is decided by subscribers. That naming convention is the “model extracts, code decides” rule enforced by the type system.

5 The lineage: state was settled before LLMs

The design being reached for in context.md — per-call session, conversation memory, slot placeholders, per-step completion conditions — is not novel, and that is the good news. It is task-oriented dialogue with slot filling, and it has a twenty-five-year paper trail.

VoiceXML, 1999

The W3C recommendation defines a form containing field item variables — slots — and a Form Interpretation Algorithm that visits each item until it is filled. Attach a grammar to each field and you get directed dialogue; attach one to the form and you get mixed initiative, where the caller may answer several fields at once and in any order, without waiting to be asked.

It also shipped the parts people rediscover painfully: noinput and nomatch event counters, escalating reprompts, and <filled> blocks that run when a field gets a value.

The columns are the same design four times. Dialogflow CX's documented behaviour is VoiceXML's FIA restated: collect required parameters in the order defined on the page, prompt with the initial fulfilment, repeat unless a reprompt handler says otherwise, escalate to a human on the third failure. Rasa adds domain-level validation for universal constraints and validate_<slot> for business ones — the same two-tier split that any implementation converges on.

What large language models actually changed

Two of the three jobs from Chapter 1, and neither of them is state.

Understanding was a hand-written SRGS grammar, then an intent classifier trained on example phrases, and is now a model that handles utterances nobody anticipated. This is a genuine step change and it is why the older systems felt brittle.

Phrasing was a static string per prompt, optionally with slots interpolated. Now it is generated, in the caller's language, varied between retries. Also a genuine step change, and the reason humanlike_sentence_answer is the one key this service cannot do without.

State did not change. A slot is still a name, a type, a value, a validity condition and a confirmation status. The step is still complete when its slots are filled and valid. The algorithm that walks the form is still the one written down in 1999.

The literature is unambiguous about why this matters. On SpokenWOZ — the benchmark built from spoken, not written, task-oriented dialogue — the best dialogue state tracker reaches 25.65% joint goal accuracy, and the best end-to-end model completes the user's request in 52.1% of dialogues.

Joint goal accuracy is the fraction of turns where every slot is correct. A quarter, on the benchmark specifically designed to look like real phone calls. That number is the argument against letting a model re-derive the booking from the transcript on each turn, and it is why Chapter 6 insists on the separation it does.

Rule

If a vocabulary is being invented for “a thing the call needs to collect”, stop and use the existing one: slot, form, step, validator, confirmation, no-match. Not because the words are better, but because every question that comes next — what happens when they answer two at once, what happens on the third failure, what happens when they correct an earlier answer — has a documented answer filed under those words.

In this repo

ai_autocalls_rust is the fifth column of that table, already built: forms/definition.rs (what a form is), forms/builder.rs (how one is assembled), forms/flow.rs (where the call is inside it), forms/parsers/ (speech to typed values, one file per type), forms/repository.rs (forms defined in Postgres, not in code). Forms are added there without writing Rust. Part II reads that design closely; it is the shortest path from where ai_assistant is to where it is going.
