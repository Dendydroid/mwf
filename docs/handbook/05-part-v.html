28 Idempotency under at-least-once delivery

Every major webhook provider — Stripe, Shopify, GitHub, Twilio — delivers with at-least-once semantics. Duplicates are not a bug in their implementation; they are the documented guarantee. A system receiving webhooks will receive the same event two, three or more times, and the only workable posture is at-least-once delivery plus idempotent effects.

This matters here more than it does for most webhook consumers, because the duplicate is not a duplicate row in a report. It is a second booking, or the same question asked twice to a caller who already answered it.

The key

Two levels, and both are needed.

Turn level
The delivery identifier. The Standard Webhooks specification — stewarded by Svix with Twilio among its partners — standardises webhook-id, webhook-timestamp and webhook-signature, and explicitly recommends using webhook-id as the idempotency key. Twilio also sends I-Twilio-Idempotency-Token to distinguish retry attempts. Whatever the platform provides, store it with the turn and short-circuit a repeat: return the same response, do not re-run the turn.
Commit level
call_id plus a hash of the slot values being committed. This is the one that survives a caller-side retry, a load-balancer replay, or a network partition that made the first response invisible. Two commits with the same call and the same content are one commit.

Returning the cached response rather than recomputing matters: a replayed turn that goes through the model again may produce a different sentence, and the caller then hears two different answers to one question.

The 15-second ceiling

Twilio enforces a 15-second limit on webhook responses. Chapter 3's numbers say a normal turn here takes 0.6–2.8 s, so there is room — but timeout_seconds = 120 is eight times the ceiling. On the bad day the timeout was sized for, the platform has given up long before this service does, and the work continues on a GPU for a connection nobody is listening to.

Rule

The inference timeout must be shorter than the caller's own timeout. A budget longer than the platform's ceiling cannot produce a useful answer; it can only consume a GPU slot that a live caller needs. Find out the platform's limit, subtract the overhead, and size the budget under it — then let Chapter 30's ladder handle the case where that is not enough.

The general shape webhook practice recommends is queue-first: acknowledge quickly and do the work behind it. That does not apply to the turn itself — the caller is waiting for the sentence, so the work is the response — but it applies exactly to everything downstream of the answer, which is Chapter 31.

The budget, not the count

“Retry twice” is the wrong policy for a caller-facing turn, because two retries of a 2.8-second call is 8.4 seconds of silence and the caller has already spoken again. The right policy is a deadline:

deadline = now + turn_budget            // what the caller will tolerate
loop {
    remaining = deadline - now
    if remaining < min_useful_attempt { break }   // no time to try again
    attempt with timeout = remaining
}
// out of budget: the ladder in chapter 30, not an error page

A retry is attempted only if there is time for it to be useful. This is the discipline the 12-Factor formulation means by owning the control flow: the application owns the loop, the stop conditions, the retries and the budget ceilings, rather than delegating them to a library's defaults.

Trap

Retrying a timeout against an overloaded inference server is how a slow system becomes an unavailable one. The first request is still occupying the GPU; the retry queues behind it; both now count against capacity. If timeouts are correlated — and under load they always are — retries multiply load precisely when load is the problem. Either do not retry timeouts, or put a circuit breaker in front of the decision.

Jitter, and why it matters on a phone line

Calls do not arrive uniformly. An outbound campaign or an IVR menu that expires produces a burst of turns within a few hundred milliseconds of each other, and a fixed backoff makes every one of them retry in unison. Full jitter — a random delay in [0, backoff] — costs nothing and breaks the synchronisation.

30 The degradation ladder

The worst outcome of any failure in this system is silence. A caller hearing nothing assumes the line dropped, starts talking, triggers barge-in, and the turn is lost regardless of what the server eventually produced.

So every failure path must terminate in a sentence. The ladder is the ordered list of ways to produce one.

#RungWhenCosts
1The answerNormalOne model call
2Repair prompt Output did not conform. Re-ask with the error and the offending output appended A second model call — only if the budget allows
3Partial extraction The sentence arrived but the metadata did not (common when streaming, Chapter 27) Nothing. Speak the sentence; treat the slots as uncollected
4Deterministic sentence No usable model output at all Nothing. A written phrase, in the right language, from a table
5Hand off Rung 4 has been used twice in this call, or the step is critical A human (Chapter 36)

Rung 2, and its limit

A repair prompt — echoing the malformed output with the parser's complaint and asking for a corrected version — has a high success rate and is the standard recovery. Two constraints: it must be inside the turn budget (Chapter 29), and it must be attempted at most once. A repair loop is indistinguishable from a hang from the caller's side.

Note that constrained decoding (Chapter 22) makes this rung largely unnecessary, which is another argument for it.

Rung 4 is the one to build first

A small table of written sentences, per language, for the handful of situations that have no model output: I'm having trouble with that, let me try again; Sorry — could you say that once more?; Let me put you through to someone who can help. They never fail, they cost nothing, and they are the floor under everything above them.

In this repo

ai_autocalls_rust has this as a first-class module — messages/phrase.rs, “every sentence, named, in every language”, with its extension guide listing “change something the caller hears” as one of the no-code tasks. ai_assistant has no equivalent: today, a VllmError becomes an ApiError and the caller's side receives {"error": "..."} with a 502 or 504, and whatever that platform does with an error response is what the caller hears.

That is a real gap and a small one to close. It is also the piece that has to exist before the timeout can safely be lowered to fit under the platform ceiling (Chapter 28), because lowering it without a fallback sentence converts slow turns into silent ones.

Rule

Never return an error to a live call. Every code path that can fail must end in a sentence in the caller's language, and the HTTP status is for the platform's logs, not for the caller's ear.

31 Commit before you say it is done

One ordering decision, stated once, because everything else in this Part is in service of it.

  1. The caller says the final yes.
  2. The submission is written to durable storage, inside the request, marked pending.
  3. Then the caller is told it is done.
  4. A background task delivers it onward and records the outcome.

Steps 2 and 3 are in that order because the booking must exist before the caller is told it does. Steps 3 and 4 are in that order because the caller must never wait on a third party: if the receiving system is slow the caller hears silence, and if it is down the caller hears a failure for something that actually succeeded.

The consequence worth stating plainly: a booking whose delivery permanently fails is still a booking. The row stays, marked failed, with the attempt count and the last error, and can be re-sent by hand. Nothing is lost, and nothing pretends to have been delivered.

Trap

The natural implementation is the wrong one. Calling the downstream API and then confirming to the caller feels more honest — only say it worked if it worked. It is not more honest; it converts a third party's latency into dead air on a phone call, and a third party's outage into a caller being told their booking failed when the data to make it is sitting in memory. The durable write is the promise; the delivery is logistics.

Where the idempotency key goes

On the submission row, as a unique constraint over (call_id, payload_hash). Then a replayed final turn (Chapter 28) hits the constraint, returns the existing row's id, and the caller hears the same confirmation. No branch, no check-then-insert race, and the database enforces it rather than the application remembering to.

In this repo

forms/delivery.rs in ai_autocalls_rust implements steps 1–4 exactly, and its module doc is the clearest statement of the reasoning in either repository — worth reading before writing the equivalent here. The one thing it does not yet have is the uniqueness constraint; save_submission is a plain INSERT. On a mimicked client that is fine. Against a telephony platform that retries webhooks, it is a duplicate booking waiting for a network blip.
