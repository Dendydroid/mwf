This Part describes engineering obligations that follow from published regulation and industry practice. It is not legal advice, and the scope of what applies depends on where callers are, what the calls are for, and who the controller is. Every item here is something an engineer must build; whether it is sufficient is a question for whoever signs off the processing.

42 request_text is personal data

The claim is not that call transcripts might contain personal data. Under GDPR, voice recordings are personal data, and a voiceprint is biometric data in the special category of Article 9, requiring explicit consent and stricter controls than ordinary text. A transcript of what a caller said is personal data about that caller from the first word.

Which means the things this system does with request_text are processing operations:

What happens todayWhat it is
Arrives in a POST bodyCollection
Sent to vLLM in a promptProcessing; the inference server is in scope
Logged verbatim to ./logs/app.log.<date>Storage — needs a retention period
Rolls daily on a mounted volumeStorage with no expiry, currently unbounded
(Planned) held in a Redis sessionStorage — the TTL is the retention period
(Planned) written into a submissionStorage, durable, with the longest life of any of these

The one that stands out is the log volume. tracing-appender rotates daily and does not delete; .gitignore ignores rotated logs and logs/.gitkeep keeps the mount point. So the current retention period for verbatim caller utterances is forever, on a host directory, with no deletion mechanism.

That is fine today, because the callers are the developer testing through the mimic client. It stops being fine on the first real call, and the fix is cheapest before there is anything to re-process.

The inference server is in scope too

A locally hosted model is a significant advantage here: nothing leaves the machine, there is no third-party processor to contract with, and no international transfer question. That is worth stating explicitly in whatever record of processing activities this ends up in, because it removes a whole class of obligation that a hosted API would create.

It does not remove the obligation to know what the inference server logs. A vLLM instance started with request logging enabled writes prompts to its own stdout, which the container runtime keeps, in a place nobody has applied a retention policy to.

43 Redaction as architecture

Real-time redaction prevents personal data from ever reaching storage. Compliance is architectural.

The distinction that matters: redacting on the way in is a property of the system; redacting on the way out is a promise that every reader honours a policy. The second one fails the first time somebody greps a log file or copies a value into a ticket.

Where the boundary goes

utterance arrives
     |
     +--> [ recogniser ] ---> named entities found
     |
     +--> redacted copy  ---> logs, traces, metrics, analytics, tickets
     |
     +--> raw copy       ---> the model, and the slot parsers
                              lives for the turn; never written down

The raw text has to reach the model — a system that redacts the name before extraction cannot extract the name. So the boundary is not “redact everything everywhere”; it is the raw text exists in memory for the duration of a turn and is never persisted, while everything durable sees the redacted copy.

The mechanism is a named-entity recogniser running on the transcript stream, masking or tokenising before the text reaches the log pipeline, the analytics store or a CRM.

What the slot map changes

Part II's design helps here in a way that is easy to miss. Once values live in a typed slot map, the system does not need the raw utterance anymore. It needs a date, a party size and a reference code, and those are typed values with known sensitivity, stored under known names, that can be individually classified, individually redacted and individually deleted.

Raw utteranceTyped slot
Classify sensitivityRequires NER, per instanceFrom the manifest, once per slot
Redact for a logRequires NER, per instanceA flag on the slot definition
Delete on requestFind it in free textDelete a field
Retain selectivelyAll or nothingPer slot, per purpose

Which gives the storage rule: keep the raw string for the length of the call (Chapter 7 wanted it for corrections and diagnosis) and let it expire with the session. Persist only typed values, and only those the submission actually needs.

Rule

Mark sensitivity in the manifest, next to the type. A slot is ordinary, sensitive or special-category, and that classification drives logging, retention and what appears in a hand-off card — automatically, from one declaration. Chapter 16's “one manifest, two consumers” becomes three.

Trap

Redacting the transcript and keeping the audio is not redaction. Where a recording exists, the audio itself has to have the segments removed, not just the text record. That is the phone platform's problem rather than this service's — but it is the kind of thing that is assumed to be handled by whoever is not handling it, and it is worth a written answer from the platform rather than an assumption.

44 Retention, erasure, and the call_id index

Retention

Quality-assurance retention for call data typically runs 30 to 90 days in practice. The number matters less than three properties: the period is justified (there is a reason it is 60 days and not 600), documented, and enforced automatically by the system rather than by somebody remembering to run a cleanup.

StorePeriodEnforced by
Redis call sessionHoursTTL — automatic, already correct in principle
Application logsDaysNothing today. Needs a rotation-and-delete policy
TracesDaysThe collector's policy
SubmissionsThe business purposeA scheduled job — and the longest-lived data here
Measure this

cache_settings.session_ttl_days = 1 is the only retention period currently expressed anywhere in the configuration, and it is expressed in days for data whose useful life is minutes. When the call session is built on top of it, that unit is the difference between a personal data footprint measured in an hour and one measured in a day. Chapter 10 made the operational argument; this is the compliance one, and they point the same way.

Erasure needs an index, and indexes are designed in

A caller asks for their data to be deleted. To honour that, every store has to be searchable by something the caller can be identified with.

This is the practical argument for using the phone system's call_id everywhere (Chapter 10) and for it being the trace id (Chapter 40). One identifier reaches the session, the submission, the logs and the traces. Without that discipline, erasure means a free-text search across a log volume, which is neither complete nor verifiable.

Rule

Every store that holds caller data carries the call_id as an indexed field, and there is one function that deletes a call from all of them. Write it before it is needed — a deletion path invented under a deadline is a deletion path that misses a store.

A useful consequence: if the redaction boundary in Chapter 43 holds, most of what would otherwise have to be found and deleted does not exist. The log tier that carries no caller content needs no erasure path, which is the cheapest possible way to satisfy the obligation.

45 Disclosure: the caller must be told

Article 50 of the EU AI Act took effect on 2 August 2026 and applies where people interact directly with an AI system. For a voice agent, the reported requirement is specific in a way that is unusual for regulation: the disclosure must be audible, in plain language, at the latest at the first interaction — not on a terms page, not on a screen the caller may not see, but spoken as part of the interaction.

Two facts have to be conveyed: that the caller is talking to a machine, and on whose behalf.

What that means for this design

It is a first-turn requirement, which makes it a state question rather than a prompt question.

  • The disclosure belongs to the call, not the turn. It happens once, and the fact that it happened is recorded on the session.
  • It must not be generated. The wording is a compliance artefact: it is reviewed, it is fixed, and it is per language. This is a phrase.rs entry (Chapter 30), not a humanlike_sentence_answer.
  • It must survive the failure paths. A call that starts with a timeout must not skip it and disclose on turn two, so the disclosure is emitted before the first model call is made, not after it succeeds.
  • It should be logged — with the call id and the exact text — because “we disclose” is a claim and a log line is evidence.
In this repo

ai_autocalls_rust has the hook already: CallEvent::CallStarted, whose comment says it exists “so a call has a beginning in the logs, and so a future greeting has somewhere to live”. That is where this goes. ai_assistant has no equivalent, because it has no notion of a call beginning — which is one more reason the call session in Part II is a prerequisite for going anywhere near a real phone line.

The neighbouring obligations

Three more things are worth knowing about before a real call happens, each of which is somebody's decision rather than an engineering choice, and each of which has an engineering consequence:

Recording consent
Several EU jurisdictions require all-party consent to record. If calls are recorded, consent is captured before recording starts, which means the disclosure turn and the consent turn interact.
Lawful basis
Whatever it is — contract, legitimate interests, consent — it determines what may be retained and for how long, which is the input to Chapter 44's table rather than an output of it.
The human alternative
Independently of regulation, a caller who asks for a human gets one (Chapter 36). This is the cheapest possible mitigation for a large class of risk and it is already in the design.
Rule

Build the disclosure before the first production call, not before the launch date. It is one phrase per language and one flag on the session, and it is the only item in this book that is both trivial to implement and capable of invalidating every call made without it.
