19 The OpenAI-compatible surface, and what vLLM adds

vLLM serves an OpenAI-compatible /v1/chat/completions. That compatibility is the reason the client in vllm.rs is forty lines and the reason the model can be swapped without touching Rust. It is also a trap, because the compatible subset is not the interesting part.

FieldCompatibleNotes
model, messagesYes—
temperature, max_tokensYesChapters 20–21
response_format: json_objectYesGuarantees valid JSON, not your JSON
guided_json / response_format: json_schemavLLMGuarantees the schema. Chapter 22
guided_choice, guided_regex, guided_grammarvLLMCheaper constraints for narrower outputs
logprobsYesThe only honest confidence signal. Chapter 23
streamYesChapter 27

The URL, and a small thing done right

LLM_URL is configured as the base ending in /v1, the way the OpenAI-compatible world writes it, and completions_url() appends the path once at startup rather than baking it into the environment where every deployment would have to repeat it correctly. It tolerates a trailing slash, and there are two tests for that.

This is worth noticing because it is the pattern for every future setting: the environment carries the thing a human knows, the code derives the thing the machine needs. A .env full of full endpoint paths is a .env where one of them is wrong.

The API key, and why it is optional

vLLM only checks a bearer token when started with --api-key. Sending one it does not expect is harmless; sending none when it does expect one is a 401. So the header follows the configuration, which is the correct asymmetry.

20 Temperature, and where zero is wrong

temperature = 0.0 is correct for what this endpoint does today, and the settings file states the reason in four words: deterministic routing. The same sentence has to land on the same function every time, or the classification is not a classification.

Two things follow that are easy to get wrong.

Zero is not actually deterministic

Greedy decoding is deterministic given identical batch composition. Under continuous batching, floating-point reduction order varies with what else is in the batch, and identical requests can produce different tokens. It is rare, and it is not a bug you can fix from the client.

The practical consequence is for testing, not production: a test that asserts an exact generated sentence is flaky by construction. Assert on the structured fields — which function was selected, whether a flag is set — and never on the prose.

The phrasing wants variety, and shares the setting

Here is the tension that arrives with multi-step forms. One schema produces two kinds of output through one sampling configuration:

KeyWantsBecause
selected_function, slot values, flagsTemperature 0The same input must route the same way, every time
humanlike_sentence_answerTemperature > 0The third re-prompt must not be word-for-word the first

Three ways out, in increasing order of cost:

  1. Leave it at zero and get variety from the prompt. Layer 4 carries an explicit instruction to vary phrasing on retries, plus two or three differently-shaped sample sentences. Cheapest, usually sufficient, and the approach the realtime-prompting guidance recommends anyway.
  2. Two calls. A cold, constrained extraction call and a warm phrasing call. Clean, and it doubles the number of GPU round trips per turn, which Chapter 3 says you cannot afford.
  3. Deterministic sentence selection. The model picks a phrase key; code selects wording from a table, rotating on the attempt counter. This is how ai_autocalls_rust works — messages/phrase.rs holds every sentence, named, in every language — and it gives perfect control and perfect reproducibility at the cost of the naturalness the model was brought in for.

Option 1 until an evaluation says otherwise.

21 Bounding generation

max_tokens is the setting whose absence caused the incident recorded in context.md, and the chapter is mostly about how to choose it again after the schema changes — because it will.

What happened

Generation was unbounded, so it could run to the end of the 4096-token context window. A repetition loop on one turn therefore held the GPU for minutes. The client's 30-second budget expired first, reqwest reported it with the same Display text it uses for a refused connection, and the caller got a 502 that said “upstream is broken” about an upstream that was merely busy.

Three separate faults, one symptom. The fix was three changes, and all three are load-bearing: a token cap, a timeout sized for the bad case, and a distinct error variant (Chapter 25).

The derivation

The current numbers: the schema has eight keys and a well-formed answer runs about 100 tokens. The cap is 256, which settings.toml describes as room for a long sentence while stopping a repetition loop.

cap = ceil(p95_observed_tokens * 2.5)

The multiplier is a judgement, not a law: it wants to be large enough that a legitimately long answer is never truncated, and small enough that a degenerate generation is cut off in well under a second of GPU time. 2.5× on a ~100-token answer gives 256, which is where the current value comes from.

Rule

Re-derive the cap whenever a key is added to the schema, and record the measurement next to the value. Every key costs generated tokens; eight keys cost about 100. A form-filling schema that emits the shared contract keys plus a step's slots will not fit in 256, and the failure mode is a truncated answer, not an error at the point of the change.

In this repo

prompts/README.md already warns about this — “past the cap a turn fails with a message naming that setting, rather than a confusing parse error” — and VllmError::Truncated carries the cap in its message so the person reading the log is told which value to change. That is the standard to hold every other setting to.

Generating fewer tokens in the first place

The cap bounds the worst case. Reducing the typical case is the latency work, and it is mostly schema design:

  • Every key is generated serially. A key nobody reads is pure latency.
  • Booleans and enums are one or two tokens. Free-text keys are not; a reasoning or notes key can cost more than everything else combined.
  • Long key names are generated too. humanlike_sentence_answer is seven tokens of pure overhead on every single turn — not enough to change on its own, but worth knowing before adding requires_clarification_question as a second one.

22 Constrained decoding

The client sends response_format: {"type": "json_object"}, and the doc comment says this is what makes parsing the content below safe enough to do directly. That is true and it is worth being precise about what it guarantees, because the guarantee is narrower than it sounds.

Three levels

ModeGuaranteesDoes not guarantee
Nothing Nothing Everything. Markdown fences, an apology, a trailing comma
json_object (current) Syntactically valid JSON. It will parse Which keys. Which types. That selected_function names a real function
guided_json / JSON Schema Valid JSON conforming to your schema: keys present, types right, enums respected That the values are correct — only that they are well-formed

The gap between rows two and three is where the interesting failures live. Under json_object, the model is told the schema in prose and asked nicely. It complies almost always. “Almost always” over thousands of calls is a steady trickle of turns where a key is missing, a float arrives as a string, or selected_function is a plausible function that does not exist.

Under a schema, those are not rare — they are impossible. The decoder masks tokens that would violate the grammar, so the output cannot leave the schema whatever the model intended, which is also the injection control noted in Chapter 17.

The backends, and the cost

vLLM picks a backend automatically; the notable one is XGrammar, which classifies tokens into context-dependent and context-independent categories to cut mask-creation time, and uses pushdown automata for context-free grammars. Comparisons find it benefits substantially from caching compiled grammars.

That is the operational point: grammar compilation is per distinct schema, and it is cached. A handful of stable schemas — one per step — compile once and are reused. A schema assembled fresh per turn with keys in varying order is a new grammar every time, and pays compilation on every request.

Rule

Schemas must be stable and few. Render them from the manifest (Chapter 16) with a deterministic key order, so the set of distinct grammars in the system equals the number of steps, not the number of turns.

Measure this

The JSON-validity rate and the schema-conformance rate, separately. Today only the first is observable, as the ratio of VllmError::Malformed to successful turns. The second — how often a syntactically valid answer is missing a key or has a value outside its enum — is currently invisible, because serde accepts anything into the flattened map. Measure it before deciding whether guided_json is worth the migration; if it is already near zero, the current mode is fine and the argument is only about injection.

The narrower constraints

A full JSON schema is not always the right tool. guided_choice constrains output to exactly one of a list, which is what pure routing is, and is dramatically cheaper than a grammar. If the architecture ever splits into a fast routing call and a slower extraction call, the routing half wants guided_choice over the function names and nothing else.

23 Confidence is not calibrated

The schema asks for "confidence": float, and the model obligingly returns 0.95. That number means considerably less than it appears to.

What is wrong with it

Self-reported confidence from an instruction-tuned model is unreliable in two documented, specific ways. It is bimodal: scores cluster at 0.95+ or 0.05−, skipping the middle range that a threshold would need. And it is class-dependent: the same 0.7 represents different actual accuracies for different classes, so one threshold cannot serve them all.

A model that says it is 95% sure may be wrong 30% of the time. The number is generated text that looks like a probability.

What to use instead

Token logprobs
Request logprobs and read the probability of the tokens that spell the chosen function name. Still not calibrated — a 0.7 logprob does not mean 70% accuracy — but it is a real measurement of the model's state rather than a generated assertion about it, and it moves monotonically with correctness, which a threshold can work with.
Thresholds fitted per class
Set them from measurement, per intent, against cost. An irreversible action wants a high-precision floor — the score at which empirical accuracy clears 0.95 on held-out calls. A read-only lookup can be far more permissive. One global threshold is the thing to avoid.
Recalibration as a recurring job
Thresholds drift with every model or prompt change. Collect routing outcomes, compute a reliability diagram, and recalibrate when expected calibration error exceeds tolerance. This only works if outcomes are recorded, which is Part VII's job.
Rule

Treat a threshold as a fitted parameter, not a constant. It is valid for one (model, prompt, schema) triple and is invalidated by a change to any of them — including a prompt edit made through the hot-reload path, which leaves no deployment record. This is a second reason for the prompt hash in Chapter 18.

In this repo

confidence currently drives nothing — it is a badge in the mimic client and a field in a log line. That is the right place for an uncalibrated number, and it should stay there until it is measured. The moment it gates a branch it has moved from the flattened map to the manifest (Chapter 16), and it needs the calibration work first.

24 One GPU, many callers

A phone line is not a chat window. Turns arrive when callers finish talking, which means arrivals are bursty and every one of them is latency-critical because somebody is holding a handset.

The queueing reality

vLLM batches continuously: requests join the running batch as capacity allows. Under load the wait is not compute, it is queueing, and queueing shows up entirely in the tail. This is why the guidance throughout this book is to watch p95 rather than the mean — the mean is dominated by the quiet periods that nobody complains about.

Two properties of this workload make it better-behaved than most:

  • Output is short and capped (Chapter 21), so no request occupies the batch for long.
  • Prompts share a long prefix (Chapter 26), so concurrent callers are cheap to co-locate.

And one that makes it worse: a stalled turn is a silent phone line, so the cost of a tail event is not a slow page, it is a caller who starts talking over the agent.

Model and quantisation

The configured model is Qwen/Qwen2.5-7B-Instruct-AWQ — a 4-bit activation-aware weight quantisation of a 7B instruct model. For a classification-and-phrasing workload with a constrained output schema, this is a sensible point on the curve: the schema does most of the structural work, so model capacity is spent on understanding rather than on format compliance.

Measure this

Quality at the schema level, before reaching for a larger model. The tempting response to a misrouted call is a bigger model. The cheaper interventions, in order: fix the capability description (Chapter 14), constrain the output (Chapter 22), add one canonical example. A scenario suite (Chapter 38) is what tells you which one worked, and without it the model swap is a guess that costs VRAM.

Trap

The context window is 4096 tokens. Nothing in the current design comes close — but layer 5 rendering, a turn window, a form manifest and a per-step schema all add prefix, and a long-running call with an unbounded window is exactly how a system discovers its context limit: mid-call, on the longest and most invested conversation of the day. Bound the window (Chapter 15) and assert the assembled length at load time.

25 A failure taxonomy that names its own cause

This chapter is short because the project already got it right, and the value is in stating the principle so it survives the next refactor.

The original failure

The first 502 this endpoint produced logged error sending request for url (...), which is all reqwest's Display prints. It hides the cause: a 30-second timeout and a refused connection read identically. Somebody looking at that line cannot tell whether the GPU container is down or merely slow, and those have opposite responses.

The taxonomy

VariantHTTPMeansFix
Timeout { budget_seconds }504 Slow or contended inference server Retryable. Investigate load, not health
Transport502 Genuinely broken upstream Check the container, the URL, the network
NoChoices502 Well-formed response with nothing in it Server-side; rare; worth alerting
Truncated { max_tokens }502 Our own cap cut the answer off Raise llm_settings.max_tokens — named in the message
Malformed { source }502 The model emitted something that is not the schema Prompt or decoding mode (Chapter 22)

The Truncated / Malformed split is the one worth studying. Both present identically — a string that will not parse — and they have opposite causes: one is a configuration value set too low, the other is a model or prompt problem. finish_reason == "length" is the only thing that distinguishes them, which is why Choice deserialises a field it otherwise has no use for, with a test asserting it survives.

Rule

One error variant per distinct operator response, not per distinct code path. Two failures that lead to the same action can share a variant; two failures that lead to different actions must not, however similar their symptom. The test is: could someone reading only the log line pick the right next step?

What to add as the system grows

  • SchemaViolation — conformed to JSON, not to the manifest. Distinct from Malformed once guided_json is in use.
  • SlotRejected — parsed, but the validator said no. Not an error at all: it is a conversational turn (Chapter 8) and must not become a 502.
  • PromptAssembly — a template referenced a variable that does not exist. Should be impossible after Chapter 18's load-time validation, which is a reason to have the variant: if it ever fires, the load-time check has a hole.

26 Prefix caching, and what breaks it

vLLM keeps KV blocks in a hash table keyed by the token sequence from the start of the request, so a request sharing a prefix with an earlier one reuses that computation. For chat workloads with long shared system prompts the reported saving is 60–80% of time-to-first-token.

Given Chapter 3's arithmetic — the model stage is the largest item in a budget this service is already over — that is the single largest latency lever available without changing hardware or architecture.

The mechanics that matter

  • Blocks are 16 tokens, and only complete blocks are cached. A prefix ending mid-block earns nothing for that block.
  • The key is the whole sequence from position zero. One differing token near the front invalidates everything after it. There is no partial credit for a prompt that matches in the middle.
  • Blocks are evicted. A prompt used once an hour will not be resident. Few, stable, frequently-used prefixes beat many rarely-used ones.
  • There is overhead when the hit rate is near zero — hashing and table comparison are not free. A workload with no shared prefixes is slightly worse off with caching on, which is a reason to measure rather than assume.

The checklist

Breaks the cacheInstead
Date or time at the top of the system promptLayer 5, at the end
Caller name or call id in the system messageLayer 5
Schema keys in map order (non-deterministic)Manifest order, always (Chapter 16)
Shuffled few-shot examplesFixed order
Per-call A/B of a layer-0 phraseSplit by deployment, not by request
Trailing whitespace that varies with the editortrim_end() — already done
In this repo

Today the system prompt is byte-identical for every caller, so the prefix is as long as it can possibly be and the hit rate should be near the theoretical maximum. This is worth measuring now, while it is trivially true, to have the baseline that shows what layering costs or saves later.

One live hazard: hot reload changes the prompt mid-flight. The turn after an edit is a guaranteed cache miss for every concurrent caller — correct behaviour, worth knowing, and a reason not to iterate on prompts against a production endpoint.

27 Streaming, and the free latency in your schema

The largest recovery available in a cascaded pipeline comes from overlapping its stages rather than speeding any of them up: stream tokens out of the model and into synthesis as they arrive, chunked at sentence boundaries. This chapter is about a version of that specific to the schema in this repository, which costs one line in a prompt file.

The observation

The schema currently emits keys in this order:

{"selected_function": ..., "confidence": ..., "language_detected": ...,
 "humanlike_sentence_answer": ..., "anger_level": ...,
 "is_hanging_up": ..., "is_greeting": ..., "requires_clarification_question": ...}

Exactly one of those keys is heard by the caller. It is fourth. Three keys are generated before the sentence starts, and four after it finishes — and generation is strictly serial, so every one of those tokens is time the line is silent.

The change

Put humanlike_sentence_answer first.

{"humanlike_sentence_answer": ..., "selected_function": ...,
 "confidence": ..., "language_detected": ..., "anger_level": ...,
 "is_hanging_up": ..., "is_greeting": ..., "requires_clarification_question": ...}

With streaming enabled, the first sentence-boundary chunk can be handed to synthesis while the remaining seven keys are still being generated. Everything after the sentence is metadata read by code, and code does not mind waiting.

Time until the caller hears anything
Non-streaming, sentence 4th (today)All ~100 tokens, then the network, then synthesis
Streaming, sentence 4th~3 keys of preamble, then the sentence
Streaming, sentence 1stThe opening brace and one key name

What it costs

Three things, all small, and one of them is already handled.

The schema order is also the badge order in the mimic client, and there is a test in vllm.rs asserting keys arrive in the order the schema lists them. Moving the answer to the front changes that order. The badge row is cosmetic and the test asserts the order matches the schema, so the fix is to update the expected order in the test — and the test correctly fails first, which is what it is for.

Parsing becomes incremental. The client currently awaits the whole body and calls serde_json::from_str. Streaming means accumulating the token stream, detecting the end of the first string value, and emitting it — while still parsing the complete object at the end for the structured fields. That is real work, and it is the only part of this change that is not free.

A truncated stream needs different handling. Today Truncated is detected from finish_reason after the fact. When streaming, the sentence may already have been spoken before the truncation is known. Which is fine — the sentence was complete; it is the metadata that was cut — but it means Truncated stops being a 502 and becomes a degraded-but-usable turn. Chapter 30.

Rule

Order the output schema by when the value is needed, not by importance or by how it reads. Anything on the critical path to the caller's ear comes first; anything consumed by code comes after. This is free, it is one line in a prompt file, and it is the only latency optimisation in this book that costs nothing.

Sentence chunking, if this is ever owned here

If synthesis is ever driven from this service rather than by the phone system, the buffer between the token stream and the synthesiser has known rules: break on sentence-ending punctuation followed by whitespace, exclude abbreviations and decimals, and enforce a minimum chunk length — around ten characters — so fragments are not sent. Word-by-word is too many requests; whole-answer is the delay this chapter exists to remove. → §IX, Chapter 49
